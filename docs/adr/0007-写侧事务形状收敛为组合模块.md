# ADR-0007：写侧「状态守卫 + 发分」收敛为组合模块

- 状态：已采纳（2026-10-17）
- 关联：`src/lib/case-transitions.ts` · `src/app/actions/review.ts` · `src/app/actions/case.ts` · 架构候选 #2

## 背景

审核通过 / 定级与重交在 action 层各自手抄同一事务形状：`updateMany({ where: { id, status: 当前状态 } })` 写时守卫，随后在审核路径上以 `awardPoints` 同事务发分。这是全库唯一没有直接测试覆盖的关键不变量——并发下守卫落空时**不能**发分。二期引用/评论积分若沿用同一手抄，会成为第三、四份副本。

## 决策

1. 写侧重复形状收进 `case-transitions.applyCaseTransition`：守卫命中才写状态补丁，写成功才发分，二者同一事务。
2. 迁移补丁仍由 `case-state` 的 `decideReview` / `decideResubmit` 产出；组合模块只负责「守卫 + 原子发分」，不重新决定状态。
3. 收款人由调用方传入（调用方已持有案例作者），模块不额外读库。
4. 建案路径（`create` + SUBMIT 发分）没有状态守卫，不属于此形状，保持 action 内直写。
5. 不引入 adapter 或可替换接口——当前只有一种存储实现，这里买的是 locality 与不变量覆盖，不是可替换性（与 ADR-0005 同一取舍）。

## 后果

- 「守卫落空 → 零写入、零发分」只有一份实现，并有直接集成测试（成功迁移发分、守卫落空不发分、无积分事件只迁移）。
- 新增写路径只要包含状态迁移，必须走此模块；`$transaction` 在案例写路径上不再手写。
- 若将来需要多写编排或第二存储实现，此模块是天然接缝候选——今天不为此加间接层。

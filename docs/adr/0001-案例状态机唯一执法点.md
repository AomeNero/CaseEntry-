# ADR-0001：案例状态机是状态写入的唯一执法点

- 状态：已采纳（2026-10-14）
- 关联：`src/lib/case-state.ts` · `src/app/actions/review.ts` · `src/app/actions/case.ts`

## 背景

初版实现中状态机模块被"咨询"而不被" obey"：真实门禁是 review.ts 里的手写字符串比较，≈22 处裸状态字符串绕过 case-state.ts；审核 schema 不耦合环节与动作，导致 `stage=FINAL + action=approve` 可无定级直接入库（grade/publishedAt/finalReviewerId 均为 null，定级积分不发）；审核与重交均为 check-then-act 裸 update，并发下可互相覆盖。

## 决策

1. 所有状态写入经由 `decideReview(current, {stage, actorId, action})` / `decideResubmit(current, rejectedStage)` 取得补丁——环节×动作全矩阵在纯函数中裁决，终审不存在"直接通过"。
2. 校验双层：`reviewActionSchema` 按环节判别（管错误文案体验），`decide*` 内部再拦（管正确性）。两层各自独立闭合漏洞。
3. 写入以 `updateMany({ where: { id, status: 期望状态 } })` 应用——不变量落在写点，count=0 即并发冲突，返回"案例状态已变化，请刷新后重试"。

## 后果

- 生命周期改动收敛到一个模块；决策矩阵可表驱动直测（含洞用例回归）。
- 不引入版本号列：本域不变量恰为"从期望状态迁移"，状态谓词即领域正确的乐观并发。
- 后续新增状态/动作时，先改 case-state 的矩阵与测试，再让 schema 与表单跟进——不允许绕过 decide 手写迁移。
